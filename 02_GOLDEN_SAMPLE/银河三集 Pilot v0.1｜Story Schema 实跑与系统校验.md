# 银河三集 Pilot v0.1
## Story Schema 实跑与系统校验

**模式：PILOT_SANDBOX**  
**Canon Writeback：默认关闭**  
**目的：验证 A/B/C/D + Continuity System 是否真正能够生产课程剧情**

---

# 0. 为什么选这三课

从当前117课课程表选择：

### Pilot 01｜第2课
**AI 回答为什么会出错，怎样核查**

课程目标：

> 理解 AI 回答可能流畅却失实，学会用可靠材料核查重要事实。

测试重点：

> **判断 / 证据 / 事实边界 / Deep Note**

---

### Pilot 02｜第23课
**给AI写一份完整、可检查的任务说明**

课程目标：

> 把真实资料任务补成可执行、可检查的任务规格，明确材料、任务、边界、输出和检查。

课程表已经给出了“城市观星短稿”的具体情境：

> 已有输入、任务和输出，但缺少边界与检查，容易把零散事实拼成没有依据的保证。

测试重点：

> **Context / 结构化任务 / 真实案例与银河剧情的分层**

---

### Pilot 03｜第51课
**做出一个可以测试的 AI 应用原型**

课程目标：

> 串联需求、生成、修改和测试，做出可测试的 AI 应用原型。

测试重点：

> **Prototype / 建造 / Bug / 测试 / NPC Registry**

# 1. Pilot 01
# 《那条太像真的答案》

## 1.1 Course Contract

**课程：** 第2课  
**核心知识：**

- 模式生成；
- AI输出可能失实；
- 核查。

**主要学习动作：**

> **核查**

**成功证据：**

用户能够：

> 把“AI说了什么”和“可靠资料实际支持什么”分开。

---

# 2. Continuity Snapshot

因为这是 Pilot，不锁正式人物首次出场顺序。

```yaml
mode: PILOT_SANDBOX

location:
  创想星域 · 临时观测舱

active_characters:
  - Toki
  - 晶老师（远程）

user_state:
  已经知道AI可以回答问题
  尚未系统学习核查

canon_writeback: false
```

这里有意**不让康缇直接出现**。

原因是我们尚未正式确定四位伙伴的首次登场时间。

如果未来正式 Canon 规定：

> 康缇进入第二星域才初遇，

那么第2课不能为了“她适合核查”而提前偷偷认识她。

这是 Pilot 第一个 Continuity 收获。

---

# 3. Story Premise

观测舱收到一份 AI 自动整理的“最新发现摘要”。

标题非常笃定：

> **“发现一颗存在生命的遥远行星。”**

拓奇盯着屏幕：

> “这个厉害。咱们是不是碰上外星人了？”

屏幕下面却还有一份来源材料。

两者看起来：

> **很像一回事，又好像不是一回事。**

---

# 4. 任务目标

系统不告诉用户：

> “AI幻觉了，请找错误。”

而是：

> **“这条消息能不能发进银河观测日志？”**

这样知识进入的是一个真实行动。

---

# 5. Evidence Packet

给用户看到三层材料：

### A｜AI摘要

内容完整、流畅、有结论。

### B｜原始资料卡

只支持：

> 某颗恒星的亮度出现周期性变化，这种数据可以帮助研究其周围是否存在行星。

### C｜日志状态

```text
待核查
可记录
已确认
```

NASA真实使用凌日法，通过恒星亮度微小下降来发现和研究系外行星；这并不等于直接看见行星，更不等于发现生命。

---

# 6. User Agency

核心互动不是：

> “AI会不会出错？”

而是：

> **你准备把这条信息标成什么状态？**

三个选项：

### A
已确认：发现生命

### B
可记录：可能发现一颗行星

### C
先不记录任何内容

这里没有非常幼稚的：

> 一个巨大正确答案 + 两个搞笑错误答案。

B最合理。

但C也不是“愚蠢答案”。

如果用户选择C，拓奇可以说：

> “够谨慎。不过原始资料里有一部分其实是能留下来的。”

---

# 7. Failure Consequence

如果用户选择A：

观测日志上立即出现：

> **“生命确认”**

随后系统要求填写：

> **证据来源：______**

填不出来。

不是红叉。

拓奇停一下：

> “哎……这个我们好像真没有。”

然后进入：

> 回资料找证据。

---

# 8. Knowledge Integration

知识不是晶老师直接讲：

> “生成式AI基于模式预测，因此可能幻觉。”

而是用户先经历：

> **一段非常像真的内容，却无法回到证据。**

最后晶老师才出现一句：

> “说得像真的，和有证据，是两件事。”

此时才给一个非常短的知识说明：

> AI可以根据模式生成很自然的答案，但自然、具体、完整，都不能替代证据。

---

# 9. Deep Note

**Voice：晶老师**

> “有些遥远行星，科学家甚至没有直接拍到它。他们只看到行星经过恒星前面时，星光暗了一点点。”

这是真实的系外行星凌日观测原理。

不考试。

拓奇只回一句：

> “看不见，还能找到？”

晶老师：

> “所以证据有时候比眼睛有意思。”

结束。

---

# 10. Episode Outcome

### Learning Delta

用户经历：

> AI答案 → 回原资料 → 找直接证据 → 调整结论。

### Character Delta

Pilot Sandbox：

> 不写正式关系变化。

### World Delta

观测记录最终被标记：

> **“候选行星信号｜生命情况未知”**

### Narrative Delta

无长期伏笔。

---

# 11. Pilot 01 结论

这集证明一个重要问题：

> **课程知识完全可以不由人物先讲，而由一个世界状态错误把它“逼出来”。**

而且“核查”天然适合被故事化。

同时暴露一个 Schema 缺口：

> 必须新增 `character_eligibility / introduction_state`。

否则 Agent 很容易因为“康缇最适合核查”就让她在正式初遇之前出现。

---

# 12. Pilot 02
# 《今晚一定看得到？》

## 12.1 Course Contract

**课程：** 第23课  
**主要知识：**

- 任务规格；
- 材料；
- 任务；
- 边界；
- 输出；
- 检查标准。

**主要学习动作：**

> **把模糊任务补成可执行规格。**

**成功证据：**

用户能够产生一份：

> **别人拿到以后知道做什么、不能做什么、怎样判断完成得对不对的任务说明。**

---

# 13. Continuity Snapshot

```yaml
mode: PILOT_SANDBOX

journey_phase:
  领航阶段

location:
  一座城市边缘的银河观测联络站

primary_companion:
  Konti

supporting_character:
  昭昭（Starbubble NPC）

user_state:
  已经知道Prompt需要说明任务和背景
  现在开始学习更完整的任务规格

canon_writeback: false
```

这里第一次测试：

> **主创星群 NPC Registry。**

昭昭不是教学伙伴。

她只是一个真实生活在银河世界里的角色。

---

# 14. Story Premise

昭昭负责一个小型观测站。

今晚站里准备给附近的人发布一张：

> **“今晚观星小提示”**

她已经把天气、观测地点、开放时间和几条观测资料交给 AI。

AI 很快写出：

> “今晚20:00来到北侧平台，你一定可以看到……”

康缇读到“一定”时停下来。

> “材料里有这句话吗？”

昭昭：

> “没有。我只让它写得吸引人一点。”

---

# 15. 当前任务

不是：

> “什么叫任务规格？”

而是：

> **把昭昭这份任务说明修到可以重新交给AI。**

屏幕显示现有规格：

```text
材料：观测站今晚资料
任务：写观星短稿
输出：100字左右
```

看起来已经不少。

但真正缺了：

> **边界 + 检查。**

---

# 16. User Agency

给用户几张可添加的“规格卡”：

### 卡1

如果资料没有确认，就不要写成保证。

### 卡2

必须使用很多形容词，让文案更吸引人。

### 卡3

成稿后检查时间、地点和观测结论是否都能在材料中找到依据。

### 卡4

可以补充AI认为可能有趣的信息。

用户需要选择最值得加入任务说明的规则。

理想选择：

> 1 + 3

---

# 17. Consequence

如果加入“自由补充有趣信息”：

重新生成后又出现了材料中没有的信息。

康缇不说：

> “你答错了。”

而是：

> “任务执行得没问题。问题在任务本身。”

这是本课最重要的一句话之一。

孩子开始理解：

> **AI做错 ≠ 永远是AI的问题。**

任务说明本身也可能有问题。

---

# 18. Context 的角色化

这一集非常适合康缇。

她不负责替用户补规格。

她不断问：

> “材料是哪份？”  
> “什么不能加？”  
> “最后谁检查？”  
> “怎样才叫写完？”

这些问题本质就是：

> Context。

但剧情里不需要说：

> “现在学习 Context Engineering。”

---

# 19. 真实生活案例为什么没有被银河吞掉

关键处理：

观星站仍然是一个正常的：

> **城市观星活动。**

没有变成：

> “今晚如果文案写错，星球会爆炸。”

没有：

> 巨大危机。

甚至整集都可以非常安静。

问题就是：

> 一张小小的活动提示不能胡说。

这正好验证了三层结构：

**银河剧情层**  
昭昭、康缇和观测站。

**现实任务层**  
城市观星短稿。

**知识行动层**  
完整、可检查的任务规格。

---

# 20. Episode Outcome

用户最终产物不是勋章，而是一张：

# 《观星短稿任务卡》

其中包含：

```text
材料
任务
边界
输出
检查
```

这是：

> **User Artifact**

而不只是：

> 完成一次答题。

---

# 21. Deep Note

这一集建议：

> **不开 Deep Note。**

原因很重要。

Deep Note 如果每课都有，就会迅速从“惊喜”变成：

> 固定栏目。

深空注脚必须保持稀缺。

---

# 22. Episode Delta

```yaml
learning_delta:
  learned:
    - 完整任务规格需要边界
    - 输出必须可检查

user_artifact:
  type: task_spec
  title: 观星短稿任务卡

canon_delta:
  none

npc_delta:
  sandbox_only:
    昭昭曾委托用户修改观星短稿任务
```

---

# 23. Pilot 02 结论

这集证明：

> **结构化知识不需要写成“宇宙装置”。**

“任务规格”不需要变成：

> 星舰五维任务晶体。

保持它就是：

> 一张任务卡。

反而更高级。

同时暴露第二个 Story Schema 缺口：

> 需要单独增加 `user_artifact`。

因为很多课程的真正学习证据，不是一次选择，而是：

> 用户最终做出的一件东西。

---

# 24. Pilot 03
# 《先别发布，它还没测完》

## 24.1 Course Contract

**课程：** 第51课  
**课程目标：**

> 串联需求、生成、修改和测试，做出一个可以测试的AI应用原型。

**核心知识：**

- 可测试原型链；
- 项目材料说明边界。

**主要学习动作：**

> **测试与迭代。**

---

# 25. Story Premise

场景：

> **光光当的工程小站。**

光光当正在试一个新工具：

# 「观测档案小助手」

输入：

> 一段观测记录。

输出三个栏目：

```text
已知事实
可能解释
还需核查
```

用途非常简单：

> 帮观测站人员先整理杂乱记录。

光光当：

> “能跑了。”

普罗看了一眼：

> “跑一次不叫能跑。”

---

# 26. 为什么这很适合普罗

普罗不需要讲：

> “Prototype 是可测试的早期版本。”

他直接做一件事：

> 找第二份输入。

第一份输入：

```text
信息完整
来源明确
格式正常
```

助手工作良好。

第二份：

```text
缺少来源
```

助手却把内容全部放进：

> **已知事实**

普罗：

> “行。现在它算原型了。”

用户可能会疑惑：

> “刚出Bug反而算？”

普罗：

> “没坏过的东西，不一定是因为做得好。也可能只是没真试过。”

人物、知识和工程思维在一句自然对话里合一。

---

# 27. User Agency

用户获得三组测试输入：

### Test A｜正常情况

信息完整、来源明确。

### Test B｜边界情况

内容存在，但来源缺失。

### Test C｜冲突情况

两份材料给出不同结果。

用户先决定：

> **先用哪一组测试最容易发现问题？**

然后观察输出。

---

# 28. Bug

现版本规则：

> 任何明确陈述都默认进入“已知事实”。

因此Test B失败。

用户不是选择：

> “有Bug / 没Bug”。

而是要完成：

# Bug Record

```text
输入：
缺少来源的观察记录

期望：
进入“还需核查”

实际：
进入“已知事实”

修改：
没有来源时，不得自动标为已知事实
```

然后重新运行同一个 Test B。

通过。

---

# 29. 第二层测试

Test C又出现新问题：

两份材料互相冲突。

助手把其中一条随机放进“已知事实”。

这时没有必要再完整修一遍。

课程本节只需让用户意识到：

> **一个原型通过一个测试，不代表已经完成。**

普罗：

> “先记下来。今天不是来把它做成终极版本的。”

这句话很重要。

原型课最容易被写成：

> 最终产品课。

---

# 30. 主创NPC测试

光光当在这一集承担：

> **需求方 / 第一位试用者。**

他不是：

> 教用户编程的人。

也不是：

> 第二个普罗。

人物功能明确分离：

### 普罗

关注：

> 能不能被测试和修改。

### 光光当

关注：

> 这东西到底能不能拿去工程站用。

这说明：

> 主创星群作为世界居民是成立的。

而且不会抢主伙伴位置。

---

# 31. 爱今为什么这一版没有加入

原先可以让爱今出现，说：

> “有没有隐私问题？”

但实际跑完 Story Profile 后，我认为：

> **不应该。**

原因有二。

第一：

这节课核心是：

> Prototype。

第二：

如果所有安全和责任问题都需要爱今出现，爱今最终会重新退化成：

> “伦理检查NPC”。

所以这一集主动不用爱今。

这也是 Pilot 得到的一个重要角色结论：

> **角色不能因为知识关键词匹配就机械出场。**

Aji ≠ safety callback。

她需要真正的人物理由才进入剧情。

### Character Delta

Sandbox：

> 用户第一次和普罗共同完成一次真实复测。

### Thread

```text
T-PILOT-03:
观测档案助手仍无法正确处理冲突材料
status: OPEN
```

这条可以用来测试：

> Thread Ledger。

不进入正式 Canon。

# 33. Pilot 03 Deep Note

这里不用宇宙科学。

可以使用：

> **工程 Deep Note。**

普罗：

> “真的航天任务也不是做完才开始测试。很多东西从设计阶段就一直在验证。”

但这句话如果未来正式进入产品，应单独从 NASA / ESA 工程资料库核验入库。

当前 Pilot：

> `REFERENCE_REQUIRED`

不直接批准。

这一点本身也验证了 Controlled Library 的治理规则：

> **觉得大概是真的 ≠ 可以直接写。**

# 34. 三集横向比较

| 项目 | Pilot 01 | Pilot 02 | Pilot 03 |
|---|---|---|---|
| 课程类型 | 判断 | 结构化 | 建造 |
| 主动作 | 核查 | 写任务规格 | 测试/迭代 |
| 主人物 | 拓奇 | 康缇 | 普罗 |
| 重要NPC | 晶老师 | 昭昭 | 光光当 |
| 知识进入方式 | Evidence | Tool | Action |
| 用户产物 | 核查后的记录 | 任务规格卡 | Bug/测试记录 |
| Deep Note | 有 | 无 | 候选待核验 |
| 世界危机 | 无 | 无 | 无 |
| 飞船损坏 | 无 | 无 | 无 |
| 选择有后果 | 有 | 有 | 有 |
| 可独立成立 | 是 | 是 | 是 |

这个结果非常好。

三集都没有使用：

> “宇宙马上出大事。”

但仍然可以有：

**悬念、人物、行动和结果。**

---

# 35. Pilot 实跑后暴露的 Story Schema 缺口

这比写三个好故事更重要。

## 缺口1｜必须增加 `mode`

```yaml
mode:
  PILOT_SANDBOX
  PRODUCTION
  CANON
```

Pilot中的设定不能默认污染正式宇宙。

---

# 36. 缺口2｜增加 Character Eligibility

```yaml
character_eligibility:
  introduced:
  available:
  first_appearance_allowed:
  relationship_state:
```

防止：

> 人物在正式认识以前就突然出现。

---

# 37. 缺口3｜课程材料与 Reference Assets 必须分开

现在的 `reference_assets` 不够。

需要：

```yaml
lesson_evidence:
  provided_materials:
  task_materials:
  answer_basis:
```

与：

```yaml
external_reference_assets:
```

严格分离。

原因：

第23课的城市观星资料属于：

> **本课教学材料。**

NASA资料属于：

> **外部事实来源。**

两者完全不是一回事。

---

# 38. 缺口4｜增加 User Artifact

```yaml
user_artifact:
  type:
  title:
  required_fields:
  evaluation_criteria:
  persistence:
```

因为银河大量课程的最佳成果应该是：

> **孩子做出的东西。**

而不是：

> 答对率。

---

# 39. 缺口5｜增加 Success Criteria

原来的 `goal` 不够。

需要：

```yaml
success_criteria:
  observable:
  test_method:
```

例如：

第51课成功不是：

> “懂了原型。”

而是：

> **用户能用至少一组非正常输入发现问题、修改并复测。**

# 40. 缺口6｜增加 Branch Convergence

轻互动不需要复杂RPG，但要记录：

```yaml
branch:
  choice_effect:
  convergence_point:
  memory_to_keep:
```

即：

> 路可以重新汇合，但不能假装用户刚才没有做过选择。

---

# 41. 缺口7｜Episode Delta 要拆成两类

### Learning Record Delta

孩子学到了什么。

### Canon Delta

宇宙真正改变了什么。

不能混在一起。

一个孩子：

> 第一次选择了错误答案

不等于银河正史里必须永久记载：

> “此人当年犯过这个错误。”

# 42. 缺口8｜角色知识匹配不能等于角色调度

需要一个字段：

```yaml
cast_reason:
  narrative_reason:
  relationship_reason:
  competency_relevance:
```

三个条件至少满足一个真正的：

> Narrative Reason。

否则：

- 有核查 → 康缇出现；
- 有原型 → 普罗出现；
- 有责任 → 爱今出现；

最后四个人又会退化成：

> 四个功能按钮。

# 43. Pilot对 Controlled Reference Library 的反向要求

经过三集实跑，B库还需要新增两列：

```text
story_use_mode
verification_required_before_release
```

`story_use_mode`：

- RULE
- EVIDENCE
- TOOL
- DEEP_NOTE
- BACKGROUND_ONLY

例如NASA Transit：

> EVIDENCE / DEEP_NOTE

而不是：

> 让角色讲一段NASA百科。

# 44. Pilot 对 Character Pack 的反向要求

C还需要未来补一块：

# Knowledge Boundary

每个角色记录：

```text
what_they_know
what_they_are_good_at
what_they_should_not_know
how_they_handle_unknowns
```

尤其：

> 康缇不能因为“擅长核查”就突然知道全部科学知识。

她仍然需要查。

这对角色可信度非常重要。

# 45. Pilot 对 Continuity 的最大结论

我们的 Continuity 不能只记录：

> **发生了什么。**

还必须记录：

> **谁当时知道什么。**

也就是：

# Epistemic Continuity

例如：

第30课才发现某个信号来源。

那么：

第18课的康缇不能因为Agent读取了完整世界圣经，就提前说出答案。

因此 Character Ledger 里的：

```text
known_information
```

应该成为硬字段。
